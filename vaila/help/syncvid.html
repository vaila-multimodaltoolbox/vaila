Pygame Multi-Video Synchronization

File: vaila/syncvid.py
Version: 0.4.12 · Updated: 2026-10-27
GUI: Frame C → Make Sync file

Purpose

Review every camera in a fast Pygame player, type each synchronization frame and the reference interval, then generate equal-duration ranges for Cut Video. Save + Cut Video opens Cut Video with the reference video and TXT already selected.

Fast workflow

Sync by events: physical time

Load the checkpoint with Load / Resume, then click Sync by events: ON. Each row imports the original Start, Sync and End as an editable ordered event list. Add more events with commas or spaces, using the same event order in every camera. Set the exact Reference clock FPS (assumed 60000/1001) and Output grid FPS (30000/1001). Container FPS does not shorten these ranges.

Review repeats using Detect repeats and D/Delete first. Physical times are assigned by piecewise linear interpolation of retained frame ordinals between events. Reference event times use original reference offsets divided by the assumed reference clock. Events must be ordered, in bounds and retained; errors identify the camera and event. No extrapolation is performed. Uniform physical spacing within each segment is an assumption. The current camera's inferred rates appear below the camera list; Validate event timing prints all rates. They do not establish acquisition FPS.

Save sync writes .events.json and a linked .checkpoint.json for resuming. Save + Cut Video exports directly. Event edits belong in Sync Video. The manifest saves events, exact rational clocks, all removal marks, method and assumptions. Legacy TXT synchronization keeps its existing behavior.

uv run --no-sync python -m vaila.syncvid --events \
  --input-dir /path/to/cameras --checkpoint /path/to/session.json \
  --reference-fps 60000/1001 --output-fps 30000/1001 --output /tmp/session.events.json
uv run --no-sync python -m vaila.cutvideo --video /path/to/cameras/c1_main.mp4 \
  --sync-file /tmp/session.events.json --output-dir /tmp/session_event_export

The output directory must be new. Without --output-dir, event export creates a timestamped directory beside the manifest. The nearest retained image is selected for each grid time; ties choose the earlier image. There are floor(span * output_fps) + 1 frames. Off-grid events stay exact calibration anchors but cannot occupy exact output timestamps.

  • <camera filename>_events.mp4: lossless RGB H.264 on the exact rational grid, no audio.
  • <camera filename>_time_map.csv: output_frame, requested_time_s, original_frame, physical_time_s, temporal_error_s, reused and exact rational times/errors. Error = selected physical time minus requested time; reused=1 means this source image was selected earlier in the output.
  • <camera filename>_retained/: lossless PNG sequence with every retained observation. _retained_times.csv associates ordinal, original frame, physical time and filename, without imposing a constant playback clock.
  • event_sync_manifest.json and README.txt: versioned calibration and audit.

Confirmed c1 events 1,15,79 and c2 events 1,20,109, with 31 removals inside c2, retain 79 and 78 samples. Both outputs have 40 frames, with events at 1,8,40. The physical span is 1.301300000 s; playback duration is 1.334666667 s. Intermediate event: 0.233566667 s. Inferred c2 rates: 55.658627 and 59.940060 fps.

Output correspondence does not imply simultaneous acquisition. Use the CSV errors. For 3D, measure 2D coordinates on retained observations, interpolate coordinates to shared times, then triangulate. Interpolation creates no new physical observations. Reconstruction is outside this mode.

Fast workflow (sync frame + FPS)

  1. Open a target directory containing at least two videos.
  2. Click a camera name, or use Page Up/Page Down.
  3. Locate the common event with playback, the timeline or frame stepping.
  4. Type its displayed 1-based frame in that camera's Sync field (the keyframe, e.g. ball contact).
  5. Repeat for every camera. Start/End of a non-reference camera are optional (see Cameras with different frame rates).
  6. Type the Reference video as a row number, filename, stem or unique fragment such as frontal.
  7. Type the inclusive Reference start and Reference end.
  8. Save sync writes the TXT and keeps the player open for more edits; Save + Cut Video saves, closes Sync Video, and opens Cut Video.

Clicking a field selects it for replacement. Tab/Shift+Tab navigates fields and Enter validates. Displayed and saved frames are 1-based and inclusive.

Cameras with different frame rates

Each camera is aligned in time at its Sync (key) frame, at its own fps, so cameras at 59.94, 50, 37.41, 30 or 22.96 fps can be cut to the same event window even when no frame is shared:

start = sync + round((reference_start - reference_sync) / reference_fps * fps)
end   = start + round((reference_end - reference_start) / reference_fps * fps)
  • Every row shows the camera's fps and frame count; the video's top bar shows fps and resolution.
  • Start/End of a non-reference row are optional. Empty: they follow the reference from Sync + fps, and the computed frames appear in grey as a preview. Typed (both): that camera is cut there and its Sync frame becomes optional.
  • On save, the terminal lists every camera's range, frames, fps and duration; a typed Start/End whose duration differs from the reference by more than one frame also shows the fps it implies. The cut keeps the file's fps.
  • Cut Video renders each range at its own fps; the sync TXT format is unchanged.

Example: reference cabine1.mp4 39–111 (keyframe 50, ball contact, 59.94 fps); cobrador_norepeat_37.41fps.mp4 keyframe 19 gives 12–57; lateral_norepeat_22.96fps.mp4 keyframe 9 gives 5–33; reporter_fundo.mp4 (30 fps) keyframe 96 gives 90–126. All cuts last 1.20–1.22 s and show the contact at 0.1835 s.

Load / Resume

Every Save sync or Save + Cut Video also writes a .json checkpoint next to the sync TXT (same name, .json extension) capturing every field's text, the current camera, the current playback frame, and the output path.

Click Load / Resume at any time to reopen a checkpoint through a file picker and restore that state:

  • All Sync frame fields, Reference video, Reference start, and Reference end are refilled.
  • The active camera and its exact playback frame are restored.
  • Works for a checkpoint saved from Save sync (an in-progress session) or Save + Cut Video (a completed one) — the status bar names which.
  • A camera the checkpoint mentions that is not present in the currently opened directory is skipped, not fatal; the status bar lists any skipped camera name.
  • A missing file, corrupt JSON, or a checkpoint missing required keys shows a clear status-bar error instead of crashing the player.

Remove repeated frames

Videos edited for YouTube or a broadcast often splice several cameras into one timeline. When a camera ran slower than the timeline, the editor repeats some of its frames: the file claims 59.94 fps but holds fewer real images.

ControlAction
Detect repeatsAnalyzes every video and marks its repeated frames
D or DeleteMarks the current frame as repeated, or keeps a marked one (safety for anything detection missed or got wrong)
Save w/o repeatsWrites repeat-free copies of every video with marks
Save sync / Save + Cut VideoAlso store the marks in the sync file; Cut Video then writes each marked camera's cut with and without them

A marked frame shows a red border and the label REPEATED; the timeline shows a red tick per mark, the camera row shows (-N), and the frame line shows the recounted number (for example Frame 45/149 (new 30/93)). Marks are saved in the Load / Resume checkpoint.

Detect repeats judges each frame as a viewer would. The frame and the previous one are blurred slightly; the motion score is the largest mean grey-level change in a 32 x 18 grid of blocks.

  • A copy re-encoded by the editor (H.264/H.265) is never pixel-identical: edges and the image top and bottom flicker a little. That codec noise scores low everywhere; a real new frame scores high where something moved.
  • The cut is chosen per video, at a gap of at least 2x between the noise group and the motion group of the sorted scores. When several such gaps exist, the one that best separates the two groups is used. Without such a gap this rule marks only changes of at most 1 grey level.
  • Interlaced sources (e.g. 50 fps material on a 59.94 timeline) repeat a frame built from the other field: the same image shifted about 1.2 px vertically. A small, purely vertical global shift is compensated before scoring again; horizontal or larger shifts are real camera motion.
  • A second rule detects alternating fields when repeat and real-motion scores overlap. Candidates require |dx| ≤ 0.1 px, 0.75 ≤ |dy| ≤ 1.75 px, and phase-correlation response ≥ 0.9. Only runs of at least three candidates with alternating vertical signs qualify. Intervals may vary, with real frames between candidates; no fixed cadence is required. A same-sign candidate ends the run and starts another. Isolated candidates and pairs do not qualify.
  • Automatic decisions combine both rules. If both apply, the audit reason is motion_threshold (exclusive counts); otherwise it is field_alternation or none.
  • Validation on the Veiga pair matched all 32 manual marks in c2_16mm.mp4, without extra or missed marks, and found zero in c1_main.mp4. The 112-frame clip exports 80 frames at about 42.814 fps. This validates this pair; other movements still need review with D.
  • On the 1080p examples: cobrador.mp4 copies scored at most 6.7 and real frames at least 40.2; lateral.mp4 5.1 against 30.6; gol.mp4 (field-shifted copies) 8.3 against 22.9: 24 repeats, about 49.88 fps (50 fps material). cabine1.mp4 and the 30 fps phone videos showed no repeats.

Save w/o repeats (or the CLI --remove-repeated, which uses the automatic marks) writes a copy of each video with marked frames in processed_norepeat_<timestamp>/, next to the videos:

FileContent
<name>_norepeat_<fps>fps.mp4H.264, distinct frames only. Container frame rate = estimated real rate, so the duration is kept; the rate is also in the file name and the comment metadata. No audio
<name>_norepeat_frames.csvnew_frame, original_frame (1-based), original_time_s
<name>_motion_scores.csvEvery analyzed video: existing frame, motion_score, repeated (1 = actually removed), shift_x_px, shift_y_px; appended phase_response, auto_repeated, auto_reason (motion_threshold, field_alternation, none). The first frame has no score/response and is never auto-marked.
norepeat_summary.csvEvery video: existing counts, rates, threshold, gap, automatic total, marked frame numbers and output; appended motion_threshold_repeats, field_alternation_repeats, manual_added_repeats, manual_kept_frames.

D changes the effective export selection (repeated), while auto_repeated and auto_reason keep the original automatic decision. Rule counts describe automatic decisions; review counts describe added removals and kept automatic marks. Without analysis (e.g. a resumed checkpoint), automatic counts are blank and current marks count as review additions. Checkpoints and sync files preserve effective marks.

Estimated real fps = fps × unique / total frames (example: lateral.mp4, 141 frames at 59.94 fps, keeps 54 frames, about 22.96 fps). The real frames are not evenly spaced in the source, so the new video spaces them evenly at the average rate; the frame map keeps the original times. Videos without repeats are listed but not rewritten.

Real FPS + Fill Start/End (after norepeat)

After saving norepeat copies, use the side-panel controls to set the true rate and align cuts:

  • Real FPS field — type e.g. 13.91 or 29.97
  • FPS this / Enter — apply to the current camera only (row shows *)
  • FPS all — apply to every camera
  • Clear the field + Enter — drop the override on the current camera
  • Fill Start/End from FPS — rewrite Start/End as the same temporal events as the reference window

Equal fps (file playback rate) → identical frame counts. Different fps → frame counts may differ; durations still match. Real FPS must match the file (e.g. 13.91 on a norepeat 13.91 file); typing 29.97 on a 13.91 file is ignored so Start/End stay the same events in time. If the container was stamped wrong at join time, retag with Frame C → Metadata info → Adjust real FPS before Fill Start/End. Overrides are stored in the Load/Resume .json checkpoint.

A shot where nothing moves at all scores like codec noise: check the motion scores before using such a copy.

Versioned sync format

# vaila sync file v2
# frame_base=1; frame ranges are inclusive
video_file    output_file    start_frame    end_frame    sync_frame
camera 01.mp4 camera_01_sync.mp4 901 1101 1001

The actual separator is a tab; CSV-style quoting supports spaces. Legacy four-field whitespace files remain readable. Saving atomically replaces old content.

With frames marked as repeated, a sixth column removed_frames lists the marked source frames inside each range (1-based). Ranges stay frame-aligned on the original timeline; Cut Video renders each synchronized cut as before and also writes <cut>_norepeat_<fps>fps.mp4 plus <cut>_norepeat_frames.csv for cameras with marks.

Direct Cut Video handoff

uv run vaila/cutvideo.py --video /path/to/reference.mp4 --sync-file /path/to/session_sync.txt

Cut Video validates every source before Pygame opens. The synchronized interval is preloaded and batch rendering remains available.

CLI

uv run vaila/syncvid.py -i /path/to/cameras
uv run vaila/syncvid.py -i /path/to/cameras -o /path/to/session_sync.txt
uv run vaila/syncvid.py -i /path/to/cameras --dry-run
uv run vaila/syncvid.py -i /path/to/cameras --remove-repeated
Safety: every typed frame is range checked; ambiguous reference text, traversal, absolute paths, external symlinks, duplicates, oversized files and invalid ranges are rejected. Handoff uses shell=False.
