Pygame Multi-Video Synchronization

File: vaila/syncvid.py
Version: 0.4.13 · Updated: 2026-10-30
GUI: Frame C → Make Sync file

Purpose

Review every camera in a fast Pygame player, type each synchronization frame and the reference interval, then generate equal-duration ranges for Cut Video. Save + Cut Video opens Cut Video with the reference video and TXT already selected.

Equalize by events (RIFE)

Open Frame C → Make Sync file, select the folder, then click Equalize by events (RIFE) at the bottom of the synchronization panel. A separate Tkinter window opens; Syncvid remains available. Outputs use the reference camera's count and exact rational FPS by default. Output FPS and Output frame count can select a different common grid. The existing Events: interpolate mode still uses Farnebäck and its grid that preserves every original.

  1. Choose Reference video (the output timeline) and Source video.
  2. Enter Reference: start, contact, end and Source: start, contact, end: original, 1-based, inclusive frames. Browse initializes start/end from counts; review contact. The Syncvid launcher prefills sync-frame values. Use Browse to refresh bounds when changing videos. Syncvid removal marks and FPS overrides do not apply.
  3. Optionally set Output FPS (decimal/fraction, with 60 and 120 shortcuts) and/or Output frame count (integer ≥3). Blank fields keep the reference grid. FPS alone calculates N = round_half_up(reference anchor span × FPS) + 1; count alone uses reference FPS; both are honored independently. 29.970 = 2997/100 differs from NTSC 30000/1001. FPS must be positive and finite. FPS-only requests calculating fewer than 3 frames are rejected.
  4. Set Practical-RIFE checkout, RIFE model directory and Output parent directory.
  5. Click Preview to review FPS/count, original/generated counts per camera, first-to-last duration (N−1)/FPS, file duration N/FPS, change relative to the reference anchor span and contact adjustments. Click Run after review; editing settings requires another preview. Progress and equivalent CLI appear in the window/terminal. Cancel export stops the worker; partial directories remain marked INCOMPLETE.

Start/end occupy frames 1 and N. Contact follows the reference interval proportion, rounded to nearest with ties up and clamped to 2…N−1. Each camera maps its own two segments linearly. All three anchors are copied exactly; fractional positions in both cameras, including the reference, use RIFE. See full output controls and audit fields.

With FPS/count blank, Roseguine example: reference c2_16mm_left.mp4 with 1,9,22; source c1_main.mp4 with 1,9,19. Both outputs have 22 frames at 2997/100 FPS, original resolution. C1 frames 1–9 and its final frame 19 are copied; the other 12 output images are generated. For output j > 9, source position is 9 + (j − 9) × 10/13. Resampling does not preserve every post-contact original in the output.

With Output FPS=60 and count blank, both have 43 frames, contact=17, span=0.7 s and file duration=43/60 s. At 120 they have 85 frames and contact=33. FPS=120 with count=31 gives a 0.25 s span and changes playback speed.

  • Each new processed_event_equalize_TIMESTAMP/ holds reference_<stem>_equalized.mp4 and source_<stem>_equalized.mp4: lossless RGB H.264, exact selected FPS, no audio. Originals are never overwritten.
  • reference_frames.csv and source_frames.csv: output/reference index, rational time, fractional source position, source neighbors, interpolation fraction, and original/generated label. Added columns record rational reference position, anchor labels, requested/effective FPS/count, output anchors and timing adjustments. reference_frame can be rational on a custom grid; default integer values remain.
  • event_equalizer.json: source paths, counts, FPS, events, output policy, RIFE revision, model code hashes, weight SHA256, GPU/runtime information, requested/effective parameters, rational durations, contact adjustments and original/generated counts per camera. README.txt states assumptions and preview; INCOMPLETE.txt remains after failure/cancellation.

Event equivalence is supplied by the operator. Uniform spacing between events and the reference clock are assumptions. Generated ball, feet and occlusion pixels may contain artifacts and are not acquired measurements. Retain measured source coordinates and provenance for quantitative 3D work. Increasing FPS creates visual estimates. Choosing FPS and count freely changes playback speed. Preview records contact shifts caused by rounding.

RIFE setup

Requires NVIDIA CUDA, CUDA-enabled PyTorch, FFmpeg and official Practical-RIFE with the matching 4.25 model bundle. The CUDA environment supplies cuDNN; avoid replacing torch through upstream's full requirements file.

RIFE is optional and its folder is yours to choose. The installers no longer install it by default (about 50 MB, so nothing lands on a disk you did not pick). Ask for it on the CUDA/GPU profile with --rife (Linux installer and bin/setup_pyproject.sh) or -Rife (install_vaila_win.ps1, bin/setup_pyproject.ps1), and choose the folder with --rife-home=DIR / -RifeHome DIR. Without them the installers print how to add it later. --no-rife / -NoRife are still accepted by old command lines. CPU/macOS profiles never install RIFE. A failed optional setup prints a retry command and leaves vailá available.

Install/reinstall only RIFE from the vailá root after installing the CUDA environment:

# Linux / WSL / Git Bash: into the vailá folder (legacy layout) ...
bash bin/setup_rife.sh
# ... or into any folder / disk you choose (portable layout, see below)
bash bin/setup_rife.sh --home /big/disk/rife
# Windows PowerShell
pwsh bin/setup_rife.ps1
pwsh bin/setup_rife.ps1 --home D:\rife

Both call bin/setup_rife.py with the existing environment using uv run --no-sync; a relative --home / --export path is relative to the folder you ran the command from. Setup clones the pinned revision, downloads the official 4.25 ZIP (~23 MB), verifies archive/model SHA256 hashes and runs CUDA inference. Repeated setup reuses verified assets. No HF login, separate cuDNN installation or Python extra is required. The NVIDIA driver must support the CUDA PyTorch build selected by vailá.

Portable RIFE folder (recommended when the vailá disk is small): --home DIR puts everything in one folder that can be copied to another disk or computer.

Choosing the folder. The equalizer uses, in this order: --rife-home DIR; the environment variable VAILA_RIFE_HOME (export VAILA_RIFE_HOME=DIR, inherited by the Syncvid button and the equalizer window); the legacy folders below. --rife-dir / --weights override just the code or the weights folder. A chosen folder without RIFE is an error that says how to fix it, never a silent fallback to another copy. setup_rife.py also installs into VAILA_RIFE_HOME when it is set and neither --home nor --root is given.

Copy an installed RIFE with no network:

--export DEST takes the install that setup would use (--home / VAILA_RIFE_HOME / legacy folders), checks the pinned revision and all SHA256 hashes, copies code and weights into DEST (portable layout) through a staging folder and runs one real CUDA inference on the copy. It never overwrites: a weight file in DEST with another hash stops the copy, and a DEST overlapping the source is refused. Repeating it is safe.

Manual cuts side by side

Open Frame C → Make Sync file, select the folder and click Manual cuts side by side (M) above the event button. M enters this mode from any sync mode; Back to synchronization (M) returns, keeping manual edits.

uv run --no-sync python -m vaila.syncvid --manual-cuts --input-dir /path/to/videos

Click a pane to select the ACTIVE camera. Playback, stepping, Go to frame, zoom and D/Delete affect only that camera. The other stays at its independent position. PgUp/PgDn, camera rows and Prev/Next video switch cameras; folders with more than two cameras display in pairs. One video works too.

  1. Navigate to the first frame to keep and press I / Set Start.
  2. Navigate to the last frame to keep and press O / Set End.
  3. Or type Start/End in each camera row: original, 1-based, inclusive frame numbers.
  4. D/Delete marks a frame for removal (red pane). Press D again to restore it. Marked originals stay visible during editing so marks can be undone.
  5. Watch each camera's kept / removed count and the Remaining / equal / diff summary. Only marks inside the interval reduce that cut's count.
  6. Save all (Ctrl+S) exports all cameras; Save current video exports only the active camera. Choose a parent for a new manual_cuts_TIMESTAMP/ directory.

Manual marks are separate from sync/repeat-detector marks; no detector runs here. Save directly writes new trims, without a sync plan, Cut Video handoff, interpolation, duplicated frames or FPS adjustment. Each source FPS is preserved: frame removals shorten duration. Equal counts imply equal duration only for equal FPS. Counts may differ if you choose. Invalid or empty cuts block export; Save current validates only the active camera.

Outputs are <original filename>_manual.mp4 (lossless RGB H.264, source rational FPS, no audio), _manual_frames.csv (1-based output/source frames and exact rational times), and manual_cuts.json (independent edits for audit/replay, not a sync file). Load manual cuts JSON restores edits. Existing files are preserved. An interrupted export keeps INCOMPLETE.txt and deletes its active partial MP4; earlier completed cameras may remain.

Progress stays visible; Cancel export / Esc stops rendering and keeps the editor open. Close exits when idle. GUI actions print equivalent CLI commands with >>.

uv run --no-sync python -m vaila.syncvid --manual-cuts --input-dir /path/to/videos \
  --cuts-file /path/to/export/manual_cuts.json --output-dir /tmp/new_manual_export

This headless replay accepts Ctrl+C; the output directory must be new. Omit output-dir to open saved cuts in the editor. Source FPS and frame counts must match the saved definitions. Synchronization checkpoints belong to the sync modes and are not manual-cut definitions.

Sync by events + interpolation

Choose a mode directly: FPS (default), Events: nearest or Events: interpolate. The selected button stays highlighted; clicking it again keeps that mode. Nearest selects a source image and creates no interpolated images. Interpolation preserves every original in each inclusive interval, even when container FPS matches. Enter ordered Start, Sync, End correspondences in every camera row; more events are supported.

Reference clock FPS starts from the reference file's rate and stays editable independently of output FPS. If an imported checkpoint clock differs from the current file (e.g. 59.94 versus 29.97), review it and click Confirm reference clock before saving. CLI users confirm by explicitly passing --reference-fps. Sessions record the confirmation and source rate. The clock and uniform source-frame spacing between events are assumptions, not measured acquisition timing.

Exact fractions compute the minimum FPS containing every original sample time. Set Max output FPS (e.g. 480) to authorize the grid: default 240, or 480 for higher rates. This is a ceiling; it does not force 480 FPS. Before saving, the panel shows exact/decimal output FPS, final count per camera and original/interpolated counts in each row. Every camera uses the same interpolation, including the one with fewer frames. Above the configured limit, validation reports the required rational rate and blocks export. No times are rounded and no originals are dropped. Raising the limit keeps the recorded reference clock unchanged; change that clock only when explicitly intended. Removal marks inside the intervals are rejected: clear them with D/Delete or revise events. Marks outside may remain for audit. All cameras need the same number of strictly increasing, valid events. There is no extrapolation beyond the extreme events.

Original positions keep their decoded pixels unchanged. Intermediate positions use OpenCV bidirectional Farnebäck, inverse motion warps and temporal blending of neighboring originals. Images are estimates: ball, feet and occlusions may show ghosting or deformation. They do not recover missing physical measurements. Review foot–ball contact visually; counts and FPS alone do not establish interpolation quality.

c1: 63, 71, 81 and c2: 54, 58, 62 with a 30000/1001 reference clock yield 37 frames per camera at 60000/1001 FPS. Events appear at output frames 1, 17, 37 (1-based). Sample span is 0.6006 s; playback duration includes the final frame's display period, about 0.617283 s.

c1: 1, 9, 19 and c2: 1, 9, 22, keeping the saved 979001/32666 reference clock, need a 480 limit. They yield 235 frames per camera at 12727013/32666 FPS (389.610390), events at 1, 105, 235. C1 keeps 19 originals and adds 216 interpolated images; C2 keeps 22 originals and adds 213. The default 240 limit blocks this session.

uv run --no-sync python -m vaila.syncvid --events --interpolate \
  --input-dir /path/to/cameras --checkpoint /path/to/session.json \
  --reference-fps 30000/1001 --output /tmp/interpolated.events.json
uv run --no-sync python -m vaila.cutvideo --video /path/to/cameras/c1_main.mp4 \
  --sync-file /tmp/interpolated.events.json --output-dir /tmp/new_interpolated_export

Use a checkpoint with the requested event lists or Start/Sync/End. Omit --output-fps: the output rate is automatic. Add --max-output-fps 480 to raise the ceiling; omit --reference-fps to retain an already confirmed saved clock. CLI precedence is explicit limit, checkpoint limit, then 240. Save sync writes manifest and resume checkpoint; Save + Cut Video exports into a new timestamped directory and prints the equivalent CLI with >>. Existing export folders are never overwritten. GUI progress supports Cancel; headless CLI prints progress and accepts Ctrl+C. Interrupted sets keep INCOMPLETE.txt, delete the active partial MP4 and have no completed set manifest. Retry into a new directory.

Exports use lossless RGB H.264 without audio, retained PNGs/timing CSV and a time-map CSV per camera. The map records 1-based output_frame, requested_time_s, exact requested_time_rational, type (original/interpolated), original_frame (empty for estimates), source_frame_left, source_frame_right, and exact interpolation_fraction. Original rows have identical neighbors and fraction 0. Legacy physical-time/error fields remain: zero assigned-time error does not measure image-estimation quality. Manifest and checkpoint record interpolation_method: farneback_bidirectional and fps_policy: auto_preserve_originals and rational-text max_output_fps; the manifest also has event_output_frames and per-camera original_output_count / interpolated_output_count. Older sessions without the ceiling use 240; sessions without an interpolation method retain nearest-image behavior. Encoder and MP4 time bases preserve the calculated rational clock exactly.

Fast workflow

Sync by events: physical time

Load the checkpoint with Load / Resume, then select Events: nearest. Each row imports the original Start, Sync and End as an editable ordered event list. Add more events with commas or spaces, using the same event order in every camera. Set the exact Reference clock FPS (initially the reference file rate, or imported clock) and Output grid FPS (30000/1001). Container FPS does not shorten these ranges.

Review repeats using Detect repeats and D/Delete first. Physical times are assigned by piecewise linear interpolation of retained frame ordinals between events. Reference event times use original reference offsets divided by the assumed reference clock. Events must be ordered, in bounds and retained; errors identify the camera and event. No extrapolation is performed. Uniform physical spacing within each segment is an assumption. The current camera's inferred rates appear below the camera list; Validate event timing prints all rates. They do not establish acquisition FPS.

Save sync writes .events.json and a linked .checkpoint.json for resuming. Save + Cut Video exports directly. Event edits belong in Sync Video. The manifest saves events, exact rational clocks, all removal marks, method and assumptions. Legacy TXT synchronization keeps its existing behavior.

uv run --no-sync python -m vaila.syncvid --events \
  --input-dir /path/to/cameras --checkpoint /path/to/session.json \
  --reference-fps 60000/1001 --output-fps 30000/1001 --output /tmp/session.events.json
uv run --no-sync python -m vaila.cutvideo --video /path/to/cameras/c1_main.mp4 \
  --sync-file /tmp/session.events.json --output-dir /tmp/session_event_export

The output directory must be new. Without --output-dir, event export creates a timestamped directory beside the manifest. The nearest retained image is selected for each grid time; ties choose the earlier image. There are floor(span * output_fps) + 1 frames. Off-grid events stay exact calibration anchors but cannot occupy exact output timestamps.

  • <camera filename>_events.mp4: lossless RGB H.264 on the exact rational grid, no audio.
  • <camera filename>_time_map.csv: output_frame, requested_time_s, original_frame, physical_time_s, temporal_error_s, reused and exact rational times/errors. Error = selected physical time minus requested time; reused=1 means this source image was selected earlier in the output.
  • <camera filename>_retained/: lossless PNG sequence with every retained observation. _retained_times.csv associates ordinal, original frame, physical time and filename, without imposing a constant playback clock.
  • event_sync_manifest.json and README.txt: versioned calibration and audit.

Confirmed c1 events 1,15,79 and c2 events 1,20,109, with 31 removals inside c2, retain 79 and 78 samples. Both outputs have 40 frames, with events at 1,8,40. The physical span is 1.301300000 s; playback duration is 1.334666667 s. Intermediate event: 0.233566667 s. Inferred c2 rates: 55.658627 and 59.940060 fps.

Output correspondence does not imply simultaneous acquisition. Use the CSV errors. For 3D, measure 2D coordinates on retained observations, interpolate coordinates to shared times, then triangulate. Interpolation creates no new physical observations. Reconstruction is outside this mode.

Fast workflow (sync frame + FPS)

  1. Open a target directory containing at least two videos.
  2. Click a camera name, or use Page Up/Page Down.
  3. Locate the common event with playback, the timeline or frame stepping.
  4. Type its displayed 1-based frame in that camera's Sync field (the keyframe, e.g. ball contact).
  5. Repeat for every camera. Start/End of a non-reference camera are optional (see Cameras with different frame rates).
  6. Type the Reference video as a row number, filename, stem or unique fragment such as frontal.
  7. Type the inclusive Reference start and Reference end.
  8. Save sync writes the TXT and keeps the player open for more edits; Save + Cut Video saves, closes Sync Video, and opens Cut Video.

Clicking a field selects it for replacement. Tab/Shift+Tab navigates fields and Enter validates. Displayed and saved frames are 1-based and inclusive.

Cameras with different frame rates

Each camera is aligned in time at its Sync (key) frame, at its own fps, so cameras at 59.94, 50, 37.41, 30 or 22.96 fps can be cut to the same event window even when no frame is shared:

start = sync + round((reference_start - reference_sync) / reference_fps * fps)
end   = start + round((reference_end - reference_start) / reference_fps * fps)
  • Every row shows the camera's fps and frame count; the video's top bar shows fps and resolution.
  • Start/End of a non-reference row are optional. Empty: they follow the reference from Sync + fps, and the computed frames appear in grey as a preview. Typed (both): that camera is cut there and its Sync frame becomes optional.
  • On save, the terminal lists every camera's range, frames, fps and duration; a typed Start/End whose duration differs from the reference by more than one frame also shows the fps it implies. The cut keeps the file's fps.
  • Cut Video renders each range at its own fps; the sync TXT format is unchanged.

Example: reference cabine1.mp4 39–111 (keyframe 50, ball contact, 59.94 fps); cobrador_norepeat_37.41fps.mp4 keyframe 19 gives 12–57; lateral_norepeat_22.96fps.mp4 keyframe 9 gives 5–33; reporter_fundo.mp4 (30 fps) keyframe 96 gives 90–126. All cuts last 1.20–1.22 s and show the contact at 0.1835 s.

Load / Resume

Every Save sync or Save + Cut Video also writes a .json checkpoint next to the sync TXT (same name, .json extension) capturing every field's text, the current camera, the current playback frame, and the output path.

Click Load / Resume at any time to reopen a checkpoint through a file picker and restore that state:

  • All Sync frame fields, Reference video, Reference start, and Reference end are refilled.
  • The active camera and its exact playback frame are restored.
  • Works for a checkpoint saved from Save sync (an in-progress session) or Save + Cut Video (a completed one) — the status bar names which.
  • A camera the checkpoint mentions that is not present in the currently opened directory is skipped, not fatal; the status bar lists any skipped camera name.
  • A missing file, corrupt JSON, or a checkpoint missing required keys shows a clear status-bar error instead of crashing the player.

Help viewer (Linux/WSL)

The Help button opens this page in a browser. It tries, in order, the BROWSER environment variable, native Linux GUI browsers (xdg-open, google-chrome, firefox, chromium) found on PATH, then wslview only when WSL interop is actually available, then Python's webbrowser module. Remove repeated frames

Videos edited for YouTube or a broadcast often splice several cameras into one timeline. When a camera ran slower than the timeline, the editor repeats some of its frames: the file claims 59.94 fps but holds fewer real images.

ControlAction
Detect repeatsAnalyzes every video and marks its repeated frames
D or DeleteMarks the current frame as repeated, or keeps a marked one (safety for anything detection missed or got wrong)
Save w/o repeatsWrites repeat-free copies of every video with marks
Save sync / Save + Cut VideoAlso store the marks in the sync file; Cut Video then writes each marked camera's cut with and without them

A marked frame shows a red border and the label REPEATED; the timeline shows a red tick per mark, the camera row shows (-N), and the frame line shows the recounted number (for example Frame 45/149 (new 30/93)). Marks are saved in the Load / Resume checkpoint.

Detect repeats judges each frame as a viewer would. The frame and the previous one are blurred slightly; the motion score is the largest mean grey-level change in a 32 x 18 grid of blocks.

  • A copy re-encoded by the editor (H.264/H.265) is never pixel-identical: edges and the image top and bottom flicker a little. That codec noise scores low everywhere; a real new frame scores high where something moved.
  • The cut is chosen per video, at a gap of at least 2x between the noise group and the motion group of the sorted scores. When several such gaps exist, the one that best separates the two groups is used. Without such a gap this rule marks only changes of at most 1 grey level.
  • Interlaced sources (e.g. 50 fps material on a 59.94 timeline) repeat a frame built from the other field: the same image shifted about 1.2 px vertically. A small, purely vertical global shift is compensated before scoring again; horizontal or larger shifts are real camera motion.
  • A second rule detects alternating fields when repeat and real-motion scores overlap. Candidates require |dx| ≤ 0.1 px, 0.75 ≤ |dy| ≤ 1.75 px, and phase-correlation response ≥ 0.9. Only runs of at least three candidates with alternating vertical signs qualify. Intervals may vary, with real frames between candidates; no fixed cadence is required. A same-sign candidate ends the run and starts another. Isolated candidates and pairs do not qualify.
  • Automatic decisions combine both rules. If both apply, the audit reason is motion_threshold (exclusive counts); otherwise it is field_alternation or none.
  • Validation on the Veiga pair matched all 32 manual marks in c2_16mm.mp4, without extra or missed marks, and found zero in c1_main.mp4. The 112-frame clip exports 80 frames at about 42.814 fps. This validates this pair; other movements still need review with D.
  • On the 1080p examples: cobrador.mp4 copies scored at most 6.7 and real frames at least 40.2; lateral.mp4 5.1 against 30.6; gol.mp4 (field-shifted copies) 8.3 against 22.9: 24 repeats, about 49.88 fps (50 fps material). cabine1.mp4 and the 30 fps phone videos showed no repeats.

Save w/o repeats (or the CLI --remove-repeated, which uses the automatic marks) writes a copy of each video with marked frames in processed_norepeat_<timestamp>/, next to the videos:

FileContent

D changes the effective export selection (repeated), while auto_repeated and auto_reason keep the original automatic decision. Rule counts describe automatic decisions; review counts describe added removals and kept automatic marks. Without analysis (e.g. a resumed checkpoint), automatic counts are blank and current marks count as review additions. Checkpoints and sync files preserve effective marks.

Estimated real fps = fps × unique / total frames (example: lateral.mp4, 141 frames at 59.94 fps, keeps 54 frames, about 22.96 fps). The real frames are not evenly spaced in the source, so the new video spaces them evenly at the average rate; the frame map keeps the original times. Videos without repeats are listed but not rewritten.

Real FPS + Fill Start/End (after norepeat)

After saving norepeat copies, use the side-panel controls to set the true rate and align cuts:

  • Real FPS field — type e.g. 13.91 or 29.97
  • FPS this / Enter — apply to the current camera only (row shows *)
  • FPS all — apply to every camera
  • Clear the field + Enter — drop the override on the current camera
  • Fill Start/End from FPS — rewrite Start/End as the same temporal events as the reference window

Equal fps (file playback rate) → identical frame counts. Different fps → frame counts may differ; durations still match. Real FPS must match the file (e.g. 13.91 on a norepeat 13.91 file); typing 29.97 on a 13.91 file is ignored so Start/End stay the same events in time. If the container was stamped wrong at join time, retag with Frame C → Metadata info → Adjust real FPS before Fill Start/End. Overrides are stored in the Load/Resume .json checkpoint.

A shot where nothing moves at all scores like codec noise: check the motion scores before using such a copy.

Versioned sync format

# vaila sync file v2
# frame_base=1; frame ranges are inclusive
video_file    output_file    start_frame    end_frame    sync_frame
camera 01.mp4 camera_01_sync.mp4 901 1101 1001

The actual separator is a tab; CSV-style quoting supports spaces. Legacy four-field whitespace files remain readable. Saving atomically replaces old content.

With frames marked as repeated, a sixth column removed_frames lists the marked source frames inside each range (1-based). Ranges stay frame-aligned on the original timeline; Cut Video renders each synchronized cut as before and also writes <cut>_norepeat_<fps>fps.mp4 plus <cut>_norepeat_frames.csv for cameras with marks.

Direct Cut Video handoff

uv run vaila/cutvideo.py --video /path/to/reference.mp4 --sync-file /path/to/session_sync.txt

Cut Video validates every source before Pygame opens. The synchronized interval is preloaded and batch rendering remains available.
